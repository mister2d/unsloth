# nix/ — AMD/ROCm Nix devShell + devenv for Unsloth Studio

## What this is

A Nix flake (`flake.nix`) plus a devenv 2.x wrapper (`devenv.yaml`, `devenv.nix`) providing an AMD-only reproducible dev environment for Unsloth Studio, sibling to the NVIDIA-oriented `debug/unsloth.nvidia/` (which uses plain devenv.sh with eval-time hardware branching, no flake).

## Hard architectural constraint — read this before changing anything

**AMD does not officially support NixOS.** AMD's ROCm compatibility matrix only lists Ubuntu, RHEL, SLES, Oracle Linux, Debian, and Azure Linux. `pkgs.rocmPackages.*` in nixpkgs is community-maintained, not AMD-built or certified, and has a documented history of drift/breakage relative to AMD's actual releases. Unsloth's own official AMD install docs use a one-line installer that `uv pip install`s AMD's official prebuilt PyTorch/bitsandbytes wheels from `download.pytorch.org/whl/rocmX.Y` — no Nix involved on their side.

Given that, **Nix's role here is deliberately minimal**: it supplies only generic dev tooling (git, cmake, ninja, python, node, uv) plus the minimal ROCm *runtime* shared libraries on `LD_LIBRARY_PATH` (`clr`, `rocblas`, `hipblas`, `rocm-smi`, `rocminfo`, `zstd`) so that AMD's own official prebuilt wheels can `dlopen()` `libamdhip64.so`/`librocblas.so`/`libzstd.so.1` etc. at runtime. Nix never builds, links against, or replaces any AMD-shipped software — it exists purely to fill the FHS-shaped hole NixOS otherwise leaves open for prebuilt manylinux wheels (see: `nix flake check`/`nix develop` don't require a real AMD GPU to succeed, because there's no eval-time hardware branching — this environment is AMD-only by construction).

Do not "improve" this by trying to nix-build torch/bitsandbytes/triton, and do not switch the Python install source away from `https://download.pytorch.org/whl/rocm7.1` (see failure-mode catalog below for why the pinned wheel tag matters) without a good reason and updating this doc.

## File map

- `flake.nix` / `flake.lock` — the AMD devShell, independently `nix flake check`/`nix develop`-able. Owns: nixpkgs pin, package list, `LD_LIBRARY_PATH`/`ROCM_PATH`/`HIP_PATH` construction, the runtime `/dev/kfd` presence shellHook banner.
- `devenv.yaml` / `devenv.lock` — devenv's input pins; consumes `flake.nix` via a `path:./` input.
- `devenv.nix` — orchestration: inlines the same `rocmPackages.*` set as the flake (kept in parity — the flake only exports `devShells`, not a `packages` output, so devenv.nix can't cleanly splice from it), plus `enterShell`/`scripts` that install the Python ML stack via a single `uv pip sync` of `requirements.lock.txt`, run the frontend build, and start backend/frontend processes. The `HIP_VISIBLE_DEVICES=0` env attr and the gated install logic (shared `installPyStack`) live here; the `lock-deps` script regenerates the lock.
- `requirements.lock.txt` — the fully pinned + hashed EXTERNAL Python dependency closure of `studio/backend/requirements/base.txt` + `studio.txt`, with `torch`/`torchvision` resolved to their `+rocm7.1` builds and `huggingface-hub` forced into transformers' `>=1.5.0,<2.0` range. Committed (like `flake.lock`/`devenv.lock`). Regenerated only by the `lock-deps` script — never hand-edited. `unsloth` is intentionally excluded (installed as a local editable via `-e . --no-deps` after sync).
- `sbom-python.cdx.json` / `sbom-nix.cdx.json` — committed CycloneDX 1.6 SBOMs for dependency traceability across upstream merges (diff them to see exactly what changed in the dependency closure). Two docs, one per layer: the Python layer (parsed from `requirements.lock.txt` by `cyclonedx-py`, run ephemerally via `uvx` — never a venv/lock dependency) and the Nix/system layer (derived in-repo from the devShell's `nix path-info -r` store-path closure; rooted in the `nixpkgs` commit from `flake.lock`, recorded in the doc metadata). Both are regenerated by the same `lock-deps` run that rewrites the lock (bundled on purpose, so they never drift) — never hand-edited. Generated with `--output-reproducible` / stable ordering so a clean regeneration produces no spurious diff. Nix components carry no `purl` (no standard `pkg:nix` scheme) and are identified by name+version + `nix:store-path`/`nix:output-hash` properties; Python components use `pkg:pypi` purls. See `nix/README.md` "Dependency traceability".
- `DEVENV.md` — user-facing usage docs (prerequisites, `devenv shell` → `setup-unsloth` → `devenv up`, scripts table, troubleshooting).
- `.gitignore` — ignores devenv/direnv generated state and the per-user `.amd-validator-host` file (see below). `devenv.lock`/`flake.lock` ARE tracked (pinned inputs).

## Failure-mode catalog (symptom → root cause → fix)

Every entry here was a real bug hit and fixed during development or maintenance of this environment. Check here first before re-diagnosing from scratch.

1. **`cd: studio/frontend: No such file or directory` / `File not found: studio/backend/requirements/base.txt`** — `devenv.nix` lives at `nix/devenv.nix`, one directory below the repo root, but scripts referenced `studio/...` as if cwd were the repo root (copied from `debug/unsloth.nvidia/devenv.nix`, which genuinely does sit at the repo root). Fix: every script anchors via `REPO_ROOT="$(cd "$DEVENV_ROOT/.." && pwd)"` and references `"$REPO_ROOT/studio/..."`, never bare relative paths.
2. **`uv pip install` warns "No virtual environment found; run 'uv venv'..."** even with `languages.python.venv.enable = true` — `uv pip install` keys off `VIRTUAL_ENV`/`--python`, not the `UV_PROJECT_ENVIRONMENT` env var that `enterShell` sets. Fix: every `uv pip install` call passes `--python "$VENV_PYTHON"` explicitly (`VENV_PYTHON="$DEVENV_STATE/venv/bin/python"`).
3. **Final `torch` ends up as a PyPI CUDA build (`torch==2.12.1+cu130`), `torch.cuda.is_available()` False, `torch.version.hip` None** — `studio/backend/requirements/base.txt` pulls `unsloth`/`unsloth-zoo` transitively, which resolves an unpinned `torch`/`torchvision` from PyPI (CUDA build) with no `--index-url` override. Installing the ROCm torch wheel *before* the requirements files doesn't help — the requirements install clobbers it right back. Fix: requirements (`base.txt`, `studio.txt`, `-e .`) run FIRST (their transient CUDA torch is discarded), then torch **and** torchvision are force-reinstalled LAST from `https://download.pytorch.org/whl/rocm7.1` with `--upgrade --force-reinstall` (torchvision must be included too — a plain PyPI torchvision alone drags CUDA torch back in transitively).
4. **`Failed to import ML libraries: huggingface-hub>=1.5.0,<2.0 is required ... but found huggingface-hub==0.36.2`** (and/or a non-fatal `cannot import name 'is_offline_mode' from 'huggingface_hub'` warning at startup) — same failure class as #3, different package. `studio/backend/requirements/studio.txt` pins `huggingface-hub==0.36.2` (a stale exact pin), which runs *after* `base.txt` resolves a modern, compatible `huggingface-hub` and downgrades it back down. `transformers` enforces `require_version("huggingface-hub>=1.5.0,<2.0")` at import time. Fix (applied): same clobber-then-correct pattern as torch — in **both** install blocks (`enterShell` and `scripts."setup-unsloth"`), immediately after the final torch/torchvision force-reinstall, `uv pip install --python "$VENV_PYTHON" "huggingface-hub>=1.5.0,<2.0" --upgrade` runs, followed by the #6 verification gate.
5. **`ImportError: libzstd.so.1: cannot open shared object file`** on `import torch` — torch's ROCm build `dlopen()`s `libzstd.so.1`, which wasn't on `LD_LIBRARY_PATH`. Fix: `pkgs.zstd` added to `packages` and to the `LD_LIBRARY_PATH` `lib.makeLibraryPath [...]` list in **both** `flake.nix` and `devenv.nix` — kept in parity, same as every other runtime lib.
6. **Post-install verification gate** — because #3 and #4 are the same failure class (an intermediate requirements install silently clobbering an authoritative package version) hitting twice, the final install steps are followed by an assertion (via the venv python) that `torch.version.hip is not None` and `huggingface_hub.__version__` falls in the required range, printing a confirmation line on success and failing loudly (non-zero exit, at `setup-unsloth`/`enterShell` time) otherwise — so a *third* occurrence of this pattern surfaces immediately instead of mid-training-run.

7. **Native SIGSEGV in `libamdhip64` stream teardown when both GPUs are visible** — on this 2-GPU host, a crash inside `hip::Device::NullStream()` → `HostQueue::terminate()` → `ReferenceCountedObject::release()` was hit in two independent, unrelated code paths whenever a process saw both GPUs: (a) the training subprocess (fixed separately in `studio/backend/core/training/worker.py`, commit `8278b430`, which restricts *that subprocess* to one GPU), and (b) the bare `import unsloth` sanity guard in `devenv.nix`'s `enterShell`, running in an unrestricted (both-GPU-visible) shell. Because the bug class surfaced twice, and training never benefits from multi-GPU visibility here anyway (`Data Parallel GPUs = 1` even with 2 visible), the fix is applied **once at the environment level** instead of per call site: `HIP_VISIBLE_DEVICES = "0"` is set in the shell `env` of **both** `flake.nix` (mkShell) and `devenv.nix` (env block), kept in parity like every other runtime env attr. This protects every Python process spawned in the shell, not just the training subprocess. It is a **default, not a hard lock** — nix env attrs are set unconditionally on shell activation, so a user who deliberately wants both GPUs can `export HIP_VISIBLE_DEVICES=0,1` (or unset it) after entering the shell. Never hardcode the *number* of GPUs anywhere; this pins to device 0 regardless of how many are present. If a future crash needs a *different* device, that's the user's `HIP_VISIBLE_DEVICES` override, not a code change.
8. **Every `devenv shell` entry re-resolves and reinstalls the whole Python graph (slow, non-deterministic churn)** — the former install was 5 separate `uv pip install` calls (`-r base.txt`, `-r studio.txt`, `-e .`, `torch torchvision --force-reinstall`, `huggingface-hub` correction), each resolving independently against live PyPI. Because `base.txt` pins nothing on `unsloth`/`unsloth-zoo` and `studio.txt` mixes exact pins with unbounded ones, packages like `fsspec`/`filelock`/`huggingface-hub` bounced between versions step-to-step and entry-to-entry (observed real churn: `fsspec 2026.6.0 → 2025.9.0 → 2026.4.0 → 2026.6.0` in a *single* shell entry). This non-determinism is *why* the clobber-then-correct dance of #3/#4 was needed at all. **Fix:** a committed, fully-pinned+hashed `nix/requirements.lock.txt` (see file map), installed with one deterministic `uv pip sync` + one `uv pip install -e . --no-deps` (swaps unsloth to the local editable source without re-resolving the locked graph). The whole install is gated behind a content-hash marker of the lock under `$DEVENV_STATE`, so a repeat entry with an unchanged lock skips it entirely (this is what fixes "reinstalls everything every time"). The lock's own emitted `--index-url`/`--extra-index-url` directives point sync at PyPI + the ROCm wheel index; `torch`/`torchvision` are pinned to explicit `+rocm7.1` local versions in the `lock-deps` override because uv's index *priority* alone does **not** reliably prefer the ROCm build over the PyPI one (empirically confirmed — a plain `torch` resolved to the PyPI CUDA build even with the ROCm index as a higher-priority extra). **This largely supersedes #3 and #4**: the lock, not a runtime force-reinstall/correction, is now what guarantees the ROCm torch and the in-range `huggingface-hub`. The post-install verification gate (#6) is deliberately **kept anyway** as defense in depth against a future lock regression — it's cheap and asserts the end state regardless of how the packages got there.

   Three follow-on bugs, all found by `amd-nix-validator` on real 2-GPU hardware and now fixed, are part of this entry:
   - **`uv pip sync` also needs `--index-strategy unsafe-best-match`** (not just the `lock-deps` compile). The lock spans PyPI + the ROCm index, and some packages (observed: `certifi`) exist on both at different versions; uv's default first-index-wins can't reconcile that and a *fresh* `devenv shell` install fails outright with "No solution found". The flag is on both the `sync` call in `installPyStack` and the `compile` in `lockDepsCmd`.
   - **The marker must be written only on success.** `installPyStack` uses an `&&`-chain (`sync && editable-install && verification`) and writes `$DEVENV_STATE/.py-deps.lockhash` only if all three pass; otherwise it prints an error and leaves no marker. Do NOT reintroduce a fall-through marker write (an earlier version did, which recorded failed installs as complete and made the fast-skip path unreachable). Also note: no `set -e`/`return`/`exit` in that snippet — it is *sourced* in `enterShell` (an `exit` would drop the user's shell) but run as a *standalone script* in `setup-unsloth` (where `return` is an error), so the `&&`-chain is the only construct that fails safe in both.
   - **Never ship both `triton` and `triton-rocm` in the lock.** torch's ROCm wheel depends on `triton-rocm`; `unsloth`/`unsloth-zoo`/`cut-cross-entropy` depend on plain `triton`; **both own the `triton/` import path**. Installed concurrently (no deterministic winner) they produce a *mixed* on-disk layout — e.g. `triton/_utils.py` from `triton-rocm 3.6.0` (no `apply_with_path`) but `triton/experimental/gluon/` from `triton 3.7.1` (which needs it). Top-level `import triton` and `torch.utils._triton.has_triton()` both *lie* (look fine), but the first real training kernel JIT dies with `ImportError: cannot import name 'apply_with_path' from 'triton._utils'` — and because the worker catches it, training exits 0 with an *empty* `loss_history` (no steps ran). Fix: `lockDepsCmd` passes `--no-emit-package triton` so `triton-rocm` is the sole provider of the `triton` module. When validating a lock regeneration, always confirm `grep '^triton' nix/requirements.lock.txt` shows *only* `triton-rocm`, and exercise a real training step (empty `loss_history` with exitcode 0 is the signature of this bug, not a success).

9. **Segfault at HIP device-init (`import torch` / first GPU call) even after a fully successful install** — this is the most subtle bug hit so far: it stays *masked* until the install actually works. While `import unsloth` was failing at `ModuleNotFoundError` (broken install, pre-#8-fixes) the process never reached HIP init, so the crash never showed; once the locked install succeeds, execution reaches HIP init and SIGSEGVs there instead. **Root cause:** `rocmPackages.clr`'s Nix setup-hook exports `HIP_DEVICE_LIB_PATH` pointing at nixpkgs' `rocm-device-libs` **bitcode** (a 7.2-era `22.0.0-rocm` build), but the pip torch is `+rocm7.1` with its own bundled 7.1 device-libs. `HIP_DEVICE_LIB_PATH` feeds the HIP compiler/JIT backend the AMDGCN **bitcode** linked into kernels at codegen — a **different mechanism** from the `LD_LIBRARY_PATH` runtime `.so`'s, and unlike those it is **NOT** forward/backward compatible across ROCm versions. The skew deterministically crashes at device-init. **This corrects an assumption previously stated in DEVENV.md** (that the 7.1-wheel/7.2-runtime skew was uniformly fine — true for runtime `.so`'s, false for device-libs bitcode). **Diagnosis technique (how it was proven): env-var elimination** — crash reproduced 6/6 with `HIP_DEVICE_LIB_PATH` set, 0/6 with it unset; unsetting `HSA_OVERRIDE_GFX_VERSION`/`HSA_PATH`/`ROCM_PATH`/`HIP_PATH` or clearing `LD_LIBRARY_PATH` did NOT help, and `HIP_VISIBLE_DEVICES` is irrelevant (this is a lib-version skew, not the multi-GPU teardown race of #7). **Fix:** `unset HIP_DEVICE_LIB_PATH` in **both** `flake.nix` (shellHook) and `devenv.nix` (enterShell) — we compile no HIP code here (only `dlopen` prebuilt-wheel runtime `.so`'s), so the var is never wanted. It must be `unset` in the shellHook/enterShell (which run *after* the setup-hook), NOT `env = ""` in mkShell (the setup-hook runs later and can re-set it) — verify empirically with `echo $HIP_DEVICE_LIB_PATH` (must be empty), don't assume. Revisit only if this env ever starts compiling HIP against the nix toolchain (it doesn't today).

   **Follow-on subtlety (the enterShell need-check must not import unsloth at all):** the top-of-enterShell `unset` is NOT sufficient for the *enterShell-internal* need-check in `installPyStack`, and neither is stripping the one var with `env -u HIP_DEVICE_LIB_PATH` — both were tried and both still SIGSEGV'd (4/4). The real root cause is deeper than any single var: enterShell runs **mid-splice**, i.e. devenv interleaves the clr setup-hook's env exports around the enterShell hook's own commands, so at the need-check line the ROCm env is only **partially assembled** (an inconsistent intermediate state). *Any* command that initializes the GPU there — `import unsloth`, `import torch` — can crash, regardless of `HIP_DEVICE_LIB_PATH`. (Validator proved the `env -u` wrap *did* clear the var in the child — child sees `None`, 0/5 crashes in isolation — yet the real in-enterShell need-check still crashed 4/4, because the crash is the incomplete splice, not the var.) Symptom: need-check crashes, forcing `need=1`, so the fast-skip never triggers and every 2nd shell entry reinstalls (validated 0/7 skips). **Fix:** the need-check only has to answer "is unsloth installed?", so don't run any code — use `importlib.util.find_spec('unsloth')`, which *locates* the module without executing it (no GPU/HIP init, completely immune to the splice-timing state; validated 0/6 clean). The post-install verification gate still `import torch`s to confirm correctness, but it runs *after* enterShell's splice completes, so that's fine. Takeaway: **never run GPU-initializing Python from inside enterShell's early logic** — only the fully-assembled post-enterShell environment is safe for that. **One more correctness flag on that probe:** it must be `"$VENV_PYTHON" -I -c ...`. enterShell `cd`s to `REPO_ROOT` first, and `REPO_ROOT` holds the in-tree `unsloth/` source + `unsloth.egg-info`; Python puts cwd on `sys.path`, so without `-I` the probe resolves `unsloth` to that source dir and false-positives "installed" even when the venv genuinely lacks it — wrongly skipping reinstall and leaving a broken venv with an intact marker. `-I` (isolated) drops cwd/PYTHONPATH/user-site while keeping the venv's own site-packages (derived from interpreter location), so the probe checks what's *actually installed*. Validated: without `-I`, an uninstalled unsloth still reports present; with `-I`, missing→reinstall and present→skip both resolve correctly.

If you hit a **new** variant of "an intermediate install step clobbers an authoritative package," first check whether the fix belongs in `requirements.lock.txt` (regenerate via `lock-deps` — the lock is now the authoritative source of package versions, per #8) rather than in a runtime install step. Only if the lock genuinely can't express it does the old runtime pattern apply: (a) let the clobber happen, (b) correct it explicitly as the last step, (c) extend the verification gate (#6) to assert the corrected state. Don't try to prevent a clobber by reordering `base.txt`/`studio.txt`/`-e .` relative to each other — their internal ordering isn't under our control and isn't the actual problem; the problem is always "the environment must end up correct regardless of what those files transitively pull."

## Real-hardware validation target — never hardcoded

This repo/branch is shared across users and hosts, so no specific SSH hostname is ever committed here or in the agent definitions. `amd-nix-validator` resolves its target host per-run, in order: a gitignored `nix/.amd-validator-host` file (`user@hostname`, one line) if present, else the `AMD_NIX_VALIDATOR_HOST` environment variable, else it asks. If you're setting up your own AMD box for validation, point at it with:

```
echo youruser@yourhost > nix/.amd-validator-host
```

(already covered by `nix/.gitignore` — never commit this file with a real value in it).

Also note: the GPU ISA target reported by `rocminfo` has varied between sessions on the *same* hostname in this project's history (`gfx1030` vs `gfx1201` observed) — never hardcode an expected ISA/gfx string anywhere in checks or docs; always read live `rocminfo` output.

## When this breaks after an upstream merge

Unsloth Studio is under continuous development; `studio/backend/requirements/*.txt`, `pyproject.toml`, and hardware-detection code all change frequently, and any of those changes can reintroduce a variant of the failure modes above. The repeatable procedure — invoke it as a single request via the `amd-nix-sync-upstream` skill (`.claude/skills/amd-nix-sync-upstream/SKILL.md`) rather than manually dispatching each step by hand; the skill runs this exact sequence end to end and reports back, still asking for explicit confirmation before anything is committed/pushed:

1. Reproduce the failure (dispatch `amd-nix-validator` if you don't have direct real-hardware access yourself).
2. Diagnose against the failure-mode catalog above first — most drift breakage repeats an already-seen category.
3. Dispatch `amd-nix-maintainer` to patch `nix/flake.nix`/`nix/devenv.nix`. This step also regenerates `nix/requirements.lock.txt` and both CycloneDX SBOMs via `lock-deps` (see below) as part of its normal duties — never a separate step to remember.
4. Dispatch `amd-nix-sbom-auditor` to diff the regenerated SBOMs (`nix/sbom-python.cdx.json`, `nix/sbom-nix.cdx.json`) against their prior committed versions and produce a risk-flagged summary — this is the "what actually changed in our dependency closure, and is it one of the packages that has already caused real breakage here" traceability check, and it should run *before* spending real-hardware time so a trivial patch-version bump doesn't get the same validation weight as a `torch`/`triton`/`huggingface-hub` change.
5. Dispatch `amd-nix-validator` to confirm on real hardware — scope the checklist to the auditor's report: a low-risk-only diff can get a lighter pass, any high-risk flag warrants the full checklist.
6. Update this catalog with anything new (symptom → root cause → fix), so the next incident resolves faster.

**Whenever `studio/backend/requirements/base.txt` or `studio.txt` changes upstream, the lock must be regenerated** (it is NOT regenerated automatically — the install is deliberately gated so shell entries stay fast). This is an `amd-nix-maintainer` task (step 3 above): inside a `devenv shell`, run `lock-deps` (which re-runs the `uv pip compile` in `devenv.nix`'s `lockDepsCmd`), review the diff to `nix/requirements.lock.txt`, confirm `torch`/`torchvision` still resolved as `+rocm7.1` builds, then commit the regenerated lock. **The same `lock-deps` run also regenerates both CycloneDX SBOMs** (`nix/sbom-python.cdx.json`, `nix/sbom-nix.cdx.json`) — this is bundled into the existing step on purpose, so there is no separate SBOM action to remember: `amd-nix-sbom-auditor` (step 4) is what actually reads the resulting diff and turns it into a risk assessment. If upstream bumps the torch version, update the `torch==...+rocm7.1` / `torchvision==...+rocm7.1` pins in `lockDepsCmd`'s override to the new version first (the compile fails loudly if the override conflicts, which is the signal to bump). A stale lock is itself a failure mode: the verification gate (#6) will catch a torch/huggingface-hub regression, but a genuinely new upstream dependency won't be installed until the lock is regenerated.

## Non-goals

Do not edit `studio/backend/requirements/*.txt` or `pyproject.toml` to fix an AMD-only version conflict. Those files are shared with `debug/unsloth.nvidia/` and the standard cross-platform installer (`install.sh`); changing them to work around a problem that only manifests in this Nix environment risks breaking those other paths. Absorb and correct the conflict inside `nix/devenv.nix`'s own install steps instead (see the catalog above).
